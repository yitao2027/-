# B100 邀请码安全漏洞修复提案

## 变更编号
B100

## 问题描述
1. **前端硬编码泄露**：500个邀请码直接写在 `frontend/src/data/INVITE_CODES.ts`，任何人都能通过开发者工具获取
2. **重复使用漏洞**：邀请码没有使用状态记录，一个码可以无限次注册
3. **前后端不一致**：前端500个码，后端只有1个码+通配符，验证逻辑完全不同步

## 影响范围
- **安全风险**：内测邀请码失去控制，任何人都能批量注册
- **业务风险**：无法追踪邀请码使用情况，无法限制注册数量
- **数据风险**：用户数据可能被恶意批量注册污染

## 修复方案
### 方案A：后端验证 + 本地数据库（推荐）
- 邀请码存储在后端 Rust 侧（JSON文件或SQLite）
- 前端只负责输入，后端验证+标记已使用
- 一码一用，记录使用时间和用户ID

### 方案B：服务端API验证（未来方案）
- 邀请码存储在远程服务器
- 需要搭建后端API服务
- 当前MVP阶段不适用

## 推荐方案：A
理由：
1. 无需额外服务器成本
2. 符合当前MVP本地模式架构
3. 可平滑迁移到未来的服务端方案

## 风险评估
- **破坏性**：中等（需要修改前后端验证逻辑）
- **回滚难度**：低（保留旧代码注释即可回滚）
- **测试复杂度**：中等（需要测试注册流程+邀请码验证）

## 时间估算
- 设计：30分钟
- 实现：2小时
- 测试：1小时
